### 2.3 交叉验证表：Liebeskind et al. 2016（8 个粗类别）

```
https://raw.githubusercontent.com/jedick/JMDplots/master/inst/extdata/evdevH2O/phylostrata/LMM16.csv.xz
```

- Liebeskind BJ, McWhite CD, Marcotte EM. *Genome Biol Evol* 8:1812–1823 (2016). "Towards consensus gene ages"
- 13 个同源推断算法的共识结果，8 个粗类别：
  Cellular_organisms / Euk_Archaea / Euk+Bac / Eukaryota / Opisthokonta / Eumetazoa / Vertebrata / Mammalia
- **用途**：和 Trigos 表做独立来源交叉验证（见 `02_构建年龄表.py` 的输出）

实测交叉验证结果：

```
可比对基因 16,889
Spearman ρ = 0.697   Kendall τ = 0.607
8 个粗类别 → 中位层号：1, 1, 1, 2, 4, 5, 8, 11   （7 对相邻全部单调，0 违反）
```

中位层号完全单调，说明两个方法完全不同的来源对"哪些基因老、哪些年轻"的判断一致。
ρ 只有 0.70 是因为 LMM16 只有 8 个取值、大量基因并列，Spearman 在强并列下会被压低。

### 2.4 置信度指标：Liebeskind 误差表

```
https://raw.githubusercontent.com/marcottelab/Gene-Ages/master/Main/main_HUMAN.csv
```

- 列含 `NumDBsContributing`、`entropy`、`NodeError`、`Bimodality`、`HGT_flag`
- 按 UniProt 索引，能和 TPPG17 join（命中 16,889 / 17,318 = 97.5%）

> ⚠️ **`NumDBsContributing` 是分母，不是支持数**（本项目踩过最贵的一次坑）
>
> 该字段的含义是"**参与投票的算法总数**"，不是"支持该年龄层的算法数"。
> 真正的共识度要自己从 13 个算法的逐层投票里算：
>
> ```
> mode_share      = 最优势层占比 = count(众数层) / n_dbs
> 支持数（近似）  = round(mode_share × n_dbs)
> ```
>
> 实测 **corr(n_dbs, mode_share) = −0.128（负相关）** ——
> 参与算法多的基因往往分歧也大。所以"高 `n_dbs`"筛出来的恰恰是**低共识**基因，
> **筛选方向与"高置信"完全相反**。
>
> **正确用法**：`05_监督分析.py --min-share 0.8`（共识度阈值），保留 **905 个**特征。
> **错误用法**：`--min-dbs 10`（本项目最初就是这么写的，结果悄悄变差但不报错）。
>
> `mode_share` 已在 `02_构建年龄表.py` 阶段一并算出并落盘到 `gene_age.tsv`，
> 供 `07_终审核对.py` 断言。详见报告 2.6 / 附录 E。

### 2.5 蛋白长度：UniProt REST API（稳健性检验 C 的前置）

Trigos 表本身**不含序列长度**，但原始表带 `Entry` 列（UniProt accession），
可以用它去 UniProt 查每个基因的蛋白长度。

```
https://rest.uniprot.org/uniprotkb/search
  ?query=(accession:P04217+OR+accession:Q9NQ94+...)&fields=length&format=tsv&size=500
```

- 产出：`10-数据/protein_length.tsv`（**17,103 个基因**，symbol / uniprot / length）
- 分布：中位 **434 aa**，均值 578 aa，范围 **13 – 8,797 aa**，< 100 aa 的有 406 个（2.4%）
- 脚本：`20-分析/93_获取蛋白长度.py`

**踩到的坑**：

| 现象 | 原因 | 处理 |
|---|---|---|
| HTTP 400 | query URL 过长——400 个 accession 时 URL 已约 **4,100 字符**，被服务端拒绝 | 批量降到 **100**；遇 4xx 直接**降批**而不是退避重试（原写法会 4 次重试 + sleep，10 分钟毫无进展） |
| 429 | 触发限流 | 退避重试（`sleep(5 * (attempt+1))`） |

- **用途**：`05_监督分析.py --min-length 100` 剔除短蛋白重跑（稳健性检验 C），
  正面回应 Moyers & Zhang 关于"短序列基因更易被判年轻"的批评。

**这个数据源带来的关键发现（前提检验）**：

拿到长度表后，本项目直接检验了 Moyers & Zhang 批评的**前提**——
"短蛋白是否真的更集中在年轻层"：

| 量 | 值 |
|---|---|
| 层号 vs 短蛋白占比 Spearman ρ | **+0.871**（p<0.001） |
| 老层 S1–S4 平均短蛋白占比 | **1.30%** |
| 年轻层 S13–S16 平均短蛋白占比 | **14.23%**（相差 **11 倍**） |
| 各层中位蛋白长度 | 从 S1 的 **454 aa** 单调降到 S16 的 **129 aa** |

结论：**该批评在本项目的年龄表上确实成立**，所以检验 C 不是可选的锦上添花，而是必要的修正。
但也要说清楚检验 C 的**定位**：Trigos 表已形成的偏倚无法被检验 C 修复，
检验 C 只是**保守性压力测试**（"即使把最易误判的基因全剔掉，方向依然成立"）。

**检验 C 的剔除量必须拆开看**（否则会把修正力度夸大 5 倍）：

| 类别 | 数量 | 是否参与过 A 组的富集检验 |
|---|---|---|
| 真正的短蛋白（< 100 aa） | **117** | 是 |
| 查不到长度信息 | **478** | 其中 **477 个**本来就没有年龄注释，**从未参与**；仅 1 个有年龄注释 |
| **合计剔除** | **595** | — |

真正从富集检验背景中移除的只有 **118 个**（117 短蛋白 + 1 无长度但有年龄注释），
背景从 **2,523 降到 2,405**。逐基因明细落在 `20-分析/filtered_genes_shortprot.tsv`。

## 2.6 细胞数的三级口径（引用时务必注明是哪一级）

同一个"细胞数"在本项目里有三个不同值，混用会导致报告数字自相矛盾：

| 口径 | 数值 | 说明 | 出处 |
|---|---|---|---|
| 母体规模 | **483,152** | Tabula Sapiens 1.0 全量，本项目**未使用** | 论文 / `ts_slice.obs.tsv` 的母体说明 |
| **本项目切片** | **28,017** | 分层抽样（每类型 ≤ 200 细胞）后实际下载的细胞数 | `ts_slice.npz` |
| **QC 后** | **22,195**（79.2%） | 最终进入全部分析的数据集 | `qc_summary.tsv` |

> 报告中出现"28,017 个细胞"时，指的是**切片**；出现"22,195"时指的是**QC 后**。
> 网页页脚三级口径并列展示，就是为了避免读者误以为是同一批细胞。
>
> 同理，"**81 种细胞类型只有 1 名供者**"这个数字是**按 QC 后细胞计**的
> （`celltype_age_profile.tsv` 的 `n_donors < 2`）。
> 切片全量表 `celltype_donor_table.tsv` 里每种类型**至少覆盖 5 名供者**，
> 之所以 QC 后掉到 1 名，是因为某些稀有类型的细胞几乎全被质控剔除了。
> 引用 81 这个数字时必须注明"按 QC 后细胞计"。

## 6. 实际采用的取数方案：HTTP Range 远程切片

> 本节是 2026-11-03 实测后的定稿版本。前面 1–5 节保留原始调研过程，
> 便于复现时了解为什么最后没走整包下载。

### 6.1 为什么不用整包下载

本机网络实测：

| 方式 | 实测速度 | 结果 |
|---|---|---|
| 单连接 urllib | 0.24 MB/s | 每个 4 MB 请求要 17 秒 |
| 8 线程并发 | 1.46 MB/s | 其中 2 个线程被直接拒绝（限流） |
| 16 线程并发 | 0.71 MB/s | **卡死**在 62% 处，进程活着但不再发数据 |
| 走本机代理 | 0.37 MB/s | 更慢 |

按最乐观的 1.46 MB/s 算，10.02 GB 需要 1.9 小时；而实测两次整包下载分别
卡死在 28%（2.85 GB）和 62%（6.22 GB）——S3 在持续大流量后会**挂住连接
且不返回错误**，只能靠超时自杀式重连。

结论：整包下载在本网络下不可行。改用「只取需要的细胞」。

### 6.2 方案原理

h5ad 的 `raw.X` 是 CSR 矩阵，第 i 行的非零元在文件里是一段**连续字节**；
HDF5 又是随机访问格式。所以可以用 HTTP Range 只取选中的行，跳过其余。

`92_远程切片.py` 的流程：

1. 远程读 `obs`（细胞类型 / 供者 / 组织 / 区室 / 测序平台）与 `raw.X` 的 `indptr`
2. 每种细胞类型取最多 200 个细胞（库中不足则全取），且**优先从同类型连续段取**，
   使选中的行落在少数连续区间里 → Range 请求数最少
3. 把选中行覆盖的非零元区间切成若干段，并发拉取（12 线程 + keep-alive 复用）
4. 落盘为 `ts_slice.npz` + `ts_slice.obs.tsv` + `ts_slice.genes.txt`

`ts_io.SliceSource` 的接口与 `ts_io.TabulaSapiens` **完全一致**，
所以下游 `01 / 03 / 04 / 05 / 06` 一行都不用改，只是数据源换了。

### 6.3 踩到的坑与处理

| 坑 | 后果 | 处理 |
|---|---|---|
| `var/feature_name` 是 **Group**（内含 categories + codes），不是 Dataset | 直接 `[:]` 报 `TypeError: Accessing a group is done with bytes or str` | 自适应读取，Dataset / Group 两种结构都支持 |
| `obs/<col>` 同样是 Group 或 Dataset 两种存法 | 同上 | `ts_io.obs()` 两种都试 |
| `codes == -1` 表示缺失 | 填 `None` 会被 `pd.Categorical` 编成 -1 组号，稀疏矩阵索引越界 | 填字符串 `"unknown"` |
| `list(h["var"].keys())` 全量遍历 | 该 h5ad 的 var 条目极多，逐个读 header 要十几分钟 | 只按候选名定点读，不遍历 |
| urllib 每次 Range 都重做 TCP+TLS 握手 | 13,695 个小请求 × 1.7 秒 ≈ 6.5 小时 | 换 `requests.Session` 复用 keep-alive 连接，实测 **0.09 → 0.54 MB/s** |
| 本机设了 `http_proxy` | requests 会自动走代理，代理侧同样限速 | `session.trust_env = False` |

### 6.4 复现

```bash
# 第一次会远程读 obs + indptr（约 3 分钟），之后走本地缓存
python 20-分析/92_远程切片.py --per-type 200 --gap-tol 0 --workers 12

# 只看代价，不下载
python 20-分析/92_远程切片.py --scan
```

参数选择由 `--scan` 扫描决定：

| per_type | gap_tol | 细胞数 | Range 段数 | 读取量 |
|---|---|---|---|---|
| 100 | 0 | 15,158 | 7,309 | 0.33 GB |
| 150 | 0 | 21,717 | 10,629 | 0.47 GB |
| **200** | **0** | **28,017** | **13,695** | **0.61 GB** |
| 300 | 0 | 39,075 | 18,739 | 0.85 GB |

`gap_tol` 越大，请求数越少但要多读很多无用字节 —— 实测带宽比请求延迟更
吃紧，所以取 `gap_tol = 0`。

元数据缓存：`10-数据/_ts_remote_cache.npz`（obs + indptr + 基因符号，约 2.2 MB）。
